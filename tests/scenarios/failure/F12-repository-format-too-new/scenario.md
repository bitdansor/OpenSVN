# F12 — 仓库格式超出当前 svn 支持范围

## 触发

把仓库的 `db/format` 首行改成 `99`（真实世界里是：同事用更新版本的 Subversion 建了
仓库，或者仓库被升级过，而本机 svn 太旧），然后检出。

```
cp -R repo repo-new
echo 99 > repo-new/db/format
svn checkout file://…/repo-new/trunk →
```

## 用户应该看到什么

- 失败，归类为 `SVN-0007`：「仓库的数据格式不在当前 svn 的支持范围内。OpenSVN 不会
  自动升级仓库，请使用与该仓库匹配的 svn，或由仓库管理员升级。」
- **不能**归类为 `SVN-0201`（网络故障）。svn 的第一句是
  `E170013: Unable to connect to a repository`，照字面映射会让用户去查网络，而真正
  的原因在第三行。

## 数据状态应该是什么

- 目标目录**不被创建**：不能留下一个半成品工作副本。
- 仓库本身**不被修改**：`db/format` 仍然是我们写进去的 `99`。这条断言直接钉住 R5
  「绝不自动升级仓库」——自动升级会不可逆地毁掉旧客户端能读的仓库。
- 完好的仓库仍然能正常检出（对照组，证明这套操作没有误伤其它东西）。

## 这个场景抓到的真实缺陷

映射表里 `E170013 → networkFailure` 排在 `E160043` 之前，而 svn 的输出顺序是
`E170013` → `E180001` → `E160043`。表内顺序即匹配顺序，所以必须把「原因」token
提到「症状」token 之前。`specifications/error-codes.md` 记录了这条规则。

## 断言清单

| 断言 | 手段 |
|---|---|
| 检出失败 | `svn checkout` 退出码非 0 |
| 真实原因是仓库格式 | stderr 含 `E160043` |
| 归类为 `SVN-0007` | `opensvn-probe map-error` |
| 提示说明不会自动升级 | `remediation` 含 `不会自动升级仓库` |
| 没有留下半成品 | 目标目录不存在 |
| 仓库没有被自动升级 | `db/format` 首行仍是 `99` |
| 对照组正常 | 同一个 svn 能检出完好的仓库 |
