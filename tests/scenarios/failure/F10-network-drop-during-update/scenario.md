# F10 — 更新途中断网

## 触发

工作副本通过 `svn://` 访问本地 `svnserve`，中间串一个 TCP 代理。代理只统计
**服务器 → 客户端**方向的字节数，累计达到阈值就把连接 RST 掉：

```
svn update → 代理 → svnserve
             └─ 转够 131072 字节后掐断
```

为什么用字节而不是「sleep 0.2 之后杀服务器」：计时是赛跑。机器快则传输早就结束，
机器慢则还没开始，同一份脚本在 CI 上时红时绿。按字节切是**确定性**的 —— 只要这次
更新需要传的字节多于阈值，中断就一定落在传输中间。

`--cut-after 0` 表示不切，同一个端口因此可以先用来检出、再切、再恢复，不需要改工作
副本的 URL。

## 用户应该看到什么

- 更新失败，归为网络类错误 `SVN-0201`：「无法连接服务器，请检查网络、代理或仓库地址。」
- 不是 `SVN-9999`（未分类），也不是「工作副本已损坏」。
- 恢复后可以重试更新并成功。

## 数据状态应该是什么

- 被传输的文件**不能是半截的**：要么是旧内容，要么是新内容，不能出现被截断的字节数。
  svn 先写临时文件再改名，这条性质值得用断言钉住。
- `svn status --xml` 仍然可解析（应用唯一的「改了什么」来源不能坏）。
- `svn cleanup` 能正常结束。
- 恢复网络后重试更新成功，文件变成新内容，`svn status` 不再报该文件。

## 断言清单

| 断言 | 手段 |
|---|---|
| 更新失败 | `svn update` 退出码非 0 |
| 失败时确实在传数据 | 代理日志出现 `byte budget exhausted`（否则场景是空过的） |
| 归类为 `SVN-0201` | `opensvn-probe map-error` |
| 文件没有被截断 | 文件字节数等于旧尺寸或新尺寸之一 |
| 工作副本仍可用 | `svn status --xml` 可解析、`svn cleanup` 退出 0 |
| 恢复后能重试成功 | 代理不再切 → `svn update` 退出 0 且内容为新版本 |
