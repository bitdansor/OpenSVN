# F8 — 提交被拒：工作副本已过期

## 触发

两个人改同一个文件。`wc-b` 先提交，`wc-a` 拿着基于旧版本的本地修改直接提交。

```
r1  tracked.txt = "initial content"
r2  wc-b: 追加 "b change"      → 提交成功
    wc-a: 追加 "a change"      → 本地 M，基于 r1
    wc-a: svn commit           → 被服务器拒绝
```

## 用户应该看到什么

- 提交**失败**，不是「部分成功」。
- 说清楚原因是「本地副本已过期」，下一步是**先更新**再提交 —— 应用侧的文案是
  `SVN-0202`：「本地副本已过期，请先 Update 再提交。」
- **不得**建议盲目重试提交。盲目重试在这里不会成功，只会重复失败；真正危险的是
  用户以为「重试几次就好了」，然后在别处（命令行）用 `--force` 之类的手段绕过去。

## 数据状态应该是什么

- 本地修改完整保留在文件里，`svn status` 仍报 `M`。
- 仓库 HEAD 不变（`svnlook youngest` 前后一致）——被拒的提交没有留下任何痕迹。
- 工作副本没有被锁死，可以直接 `svn update` 继续工作。

## 为什么它是场景而不是单元测试

单元测试只能喂一段**写死的 stderr** 给映射表，证明 `E160028 → outOfDate`。它无法证明
真实的 svn 在被拒之后确实保留了本地修改、确实没有推进仓库版本。这两条才是用户会
踩到的东西，所以这里跑真实的 svn。

「应用会怎么归类」这一半由 `opensvn-probe` 补上：它把真实 stderr 送进
`SVNErrorMapper`，输出应用实际会用的错误码。

## 断言清单

| 断言 | 手段 |
|---|---|
| 提交退出码非 0 | `svn commit` 退出码 |
| 原因是「过期」 | stderr 含 `E160028`（svn 自己输出的 token） |
| 应用归类为 `SVN-0202` | `opensvn-probe map-error` |
| 提示是「先 Update」而不是「重试」 | `remediation` 含 `先 Update 再提交` |
| 本地修改仍在 | 文件内容 + `svn status --xml` 里有 `modified` 条目 |
| 仓库未被改动 | `svnlook youngest` 前后相同 |
